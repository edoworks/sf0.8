# Automation-First Production Readiness

Status: active factory contract, 2026-09-18. This is a release-evidence
contract, not a second product lifecycle or dashboard.

## Rule

Every production criterion defaults to machine-verifiable evidence. A criterion
that cannot be automated must explicitly record its requirement, automation
status, concrete reason automation is insufficient, the physical or empirical
property involved, whether it blocks production, the claim it supports, and
the evidence that satisfies it. `manual review required` is not sufficient.

The canonical schema is `.factory/automation/release-criteria.json`. It is a
source index, not a copy of product requirements. Product repositories declare
their own criteria and evidence in `docs/automation/release-criteria.json`.
Validate the resolved canonical manifests with
`python3 scripts/validate-automation.py`.

Allowed criterion classifications are `AUTOMATED`, `SIMULATOR`, `SANDBOX`,
`DEVICE`, `EMPIRICAL`, `HUMAN-AUTHORITY`, and `NOT-APPLICABLE`. Bundle
categories independently report `VERIFIED`,
`PARTIALLY VERIFIED`, `UNVERIFIED`, or `NOT APPLICABLE`; there is deliberately
no aggregate production-readiness score.

  passed, including the actionable sample path and the unavailable-recognition
  path that must not manufacture a task from fallback text.

The former human gates were caused by product evidence being split between
runbooks, issue comments, device notes, and scripts, while the factory had no
machine-readable mapping from a release claim to an evidence class. Some gates
were genuine: physical audio/haptics, target-animal behavior, subjective
delight, VoiceOver/assistive-technology use, and App Store/TestFlight
infrastructure. Other gates were merely unimplemented seams: relaunch,
corruption, failure recovery, visual checkpoints, accessibility audits, and
deterministic provider behavior.

The corrective boundary is:

| Property | Default evidence | Escape |
|---|---|---|
| Application logic, persistence, migration, malformed data | unit/integration tests | none unless the property is outside software |
| Critical user goals and relaunch | XCTest/XCUIAutomation journeys | explicit criterion escape |
| Appearance and semantic checkpoints | generated screenshots and visual diff | human design judgment only for subjective quality |
| Machine-verifiable accessibility | XCUI accessibility audit and Dynamic Type matrix | assistive-technology observation when the claim requires it |
| Purchases | StoreKit Testing configuration and transaction tests | Sandbox/TestFlight for App Store infrastructure |
| Model/service dependency | production interface plus deterministic test provider | live-model evaluation for live behavior claims |
| Performance | XCTest/Xcode/Instruments budgets | device evidence where hardware changes the claim |
| Publication, signing, release authority | human authorization | never automated away |

## Repository-grounded 5-Whys

**Why does sf0.8 still require humans for release evidence software could
verify?**

1. The release audit asks for manual/device review because no single artifact
   binds each criterion to its strongest available evidence.
2. Evidence was organized around historical product runbooks and issue gates,
   not executable journeys and machine-readable claims.
3. The factory had deterministic policy validators, but no reusable convention
   for product scenarios, critical journeys, screenshots, accessibility output,
   or bundle status.
4. Factory v0.1 correctly avoided a speculative executor, but it left the
   product-side test contract implicit; that made missing automation look like
   a human requirement.
5. The deepest practical cause is an undefined release-criterion denominator
   and no enforced default that an unautomated criterion must justify itself.

Immediate correction: add the declarative criteria, world, journey, and bundle
schemas plus a validator and CI check. Root-cause correction: require every
future product release claim to name its evidence class before implementation;
the contract is rejected when an unverified production blocker or vague manual
escape appears. The validator is the recurrence guard.

## Intent Compiler readiness

The proposed product is a near-human-free software-production candidate if its
interfaces remain explicit: deterministic model gateway, structured prompt
contract, versioned persistence, semantic diff, evaluation runner,
import/export, and scenario launch arguments. Its critical journey is
fresh-install -> describe intent -> compile -> inspect -> save -> terminate ->
relaunch -> edit -> diff -> evaluate -> compare -> accept -> export.

Unit tests cover transformation and diff rules; integration tests cover
persistence and evaluation; XCUI covers the journey and screenshots;
accessibility audits cover machine-detectable UI defects; deterministic model
providers cover success, empty/malformed/refusal/timeout/rate-limit/unavailable,
partial, huge, Unicode, slow, and tool-failure responses; live-model suites
evaluate only version-sensitive model behavior. The remaining blockers are
only claims that depend on live model versions, physical hardware, target-user
outcomes, or human release authority.

The modeled assessment is `docs/automation/intent-compiler-assessment.json`.
Its current ceiling is 6 automated/simulator criteria, 1 empirical live-model
criterion, and 1 human-authority release criterion. It has no unjustified
manual criterion.

## Smallest human surface

Humans decide product value, subjective experience, target-user outcomes,
physical properties not simulated by Apple tooling, legal/privacy/IP meaning,
and irreversible publication or release. Repeatable software verification is
not a human responsibility after the criterion has an executable evidence
path.
